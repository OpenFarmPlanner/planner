# Season-effective growing-area geometry

Decision record for [#916](https://github.com/OpenFarmPlanner/planner/issues/916), 2026-11-25. Location, parcel and bed IDs continue to identify physical growing areas. A durable geometry record describes what is known about an area from an effective date. A different physical area uses a new identity. Presentation coordinates stay global. Both List and the [Map design](growing-area-map-design.md) use the same history foundation before they write physical changes to a used area.

## Current behavior and gaps

| Existing path | Relevant behavior |
| --- | --- |
| [Location, Field and Bed models](../backend/farm/models/structure.py) and [structure serializers](../backend/farm/structure/serializers.py) | Each owns current measurements. Location computes area from its dimensions. Field and Bed derive `area_sqm` on save when both dimensions are set. Location latitude/longitude and address are hints for finding a place. There is no season dimension or geographic footprint on these rows. |
| [Structure views](../backend/farm/structure/views.py) and [Growing Areas inline edits](datagrid-architecture.md#growing-areas-edit-and-save-measurements) | List and details submit ordinary CRUD. Field dimension changes already lock the parcel against concurrent individual stem writes and reject sizes excluding stems. Bed edits, bulk creation and duplication can create or replace present measurements. Parent foreign keys are ordinary fields. The same change's behavior must be consistent across all mutation paths. |
| [Schematic layout service](../backend/farm/services/bed_layouts.py) and [Graphic](../frontend/src/pages/GraphicalFields.tsx) | Location's schematic boundary origin and separate FieldLayout/BedLayout offsets are presentation coordinates. Neither a drag nor a view change provides evidence of physical geometry. |
| [Planning model](../backend/farm/models/planning.py) and [history mixins](../backend/farm/common/mixins.py) | Plans refer to stable bed or parcel IDs. Both references, as well as hierarchy foreign keys, use cascade deletion today. Normal deletion of a used parent can therefore delete historical plans or descendants. Existing revision writes record changes, but do not make that deletion a safe agronomic workflow. |
| [Bed capacity](../backend/farm/services/bed_capacity.py), [season copy](../backend/farm/services/seasons.py) and [parcel rotation](../backend/farm/services/parcel_rotation_copy.py) | Capacity reads the current bed area while comparing dated occupancy. Rotation scales the copied allocation against current sizes on both sides and stores a quantity/bed-area basis to avoid cumulative drift. A historical or future preview needs date-effective sizes and availability on each side. |
| [Yield comparison](../backend/farm/services/yield_comparison.py) | Historical yield rates already distinguish recorded harvested area and planned allocation. Location/parcel grouping follows current foreign keys. Preserve those denominators and resolve the historical parent when filtering or labeling a past result. |
| [Project history and retention](versioning-and-history.md#retention-anchors) | EntityRevision records snapshots and supports Undo and project restore. Cleanup keeps a rolling 30-day window and retention anchors. The surviving snapshots neither guarantee a full seasonal geometry timeline nor prove when a historical measurement applied. |

Heirloom documents bed dimension changes that begin in the selected season and carry forward while earlier seasons keep their figures. It also documents a block's first season. It may unassign affected plantings when beds are removed. OpenFarmPlanner takes the effective-season behavior and preserves planted references until an explicit safe resolution is available. [Heirloom dimension changes](https://heirloom.ag/faq/if-i-change-a-blocks-beds-does-it-change-my-past-seasons) · [Heirloom first season](https://heirloom.ag/faq/why-doesnt-my-new-block-show-in-last-season) · [Heirloom removal](https://heirloom.ag/faq/what-happens-to-my-plantings-if-i-delete-a-block).

farmOS treats minor changes to fixed land assets as corrections and recommends a new asset with the old one archived for substantial physical change. OpenFarmPlanner uses that identity distinction for changes to different soil. A resize of substantially the same growing area keeps its identity with a new dated version, as approved in #916. [farmOS location and fixed assets](https://farmos.org/model/logic/location/).

## Identity and ground history

| Grower's intent | Stored result and example |
| --- | --- |
| Arrange the schematic | Drag a parcel and its beds for a clearer diagram. Update only the existing schematic layout. |
| Initially find the area or correct a measurement | A GPS point is six metres off, or the entered width should be 1.2 m. Select the affected version and correct that record after a preview when already used. Initial georeferencing of the existing place is a correction with provenance. The timeline, ID and recorded plan facts stay intact. |
| Resize the same area | Bed 42 grows from 10 to 15 m² from the autumn-start season. Add a 15 m² version for ID 42. The old interval retains 10 m² and the planting on it. |
| Relocate onto different soil | Retire ID 42 from the chosen boundary and create ID 73 at the new location. Existing plans stay attached to 42. A continuing planting that conflicts blocks the operation until it has an explicit supported resolution. |
| Split or merge | Splitting 42 creates new IDs 73 and 74. Merging them later creates another new ID. Retire the inputs, keep their plans, and record the source/destination relationship for the affected ground. |
| Retire an area | Retire Bed 12 from the selected season. Show it where it was historically available. Exclude it from new assignments from the effective date. |
| Add a new area | A new unused bed starts in the selected season and can be set up directly. Correct that unused version through the normal form. Preserve a separately scheduled later version if one exists. |
| Earlier history is unknown | A legacy bed first has trusted measurements at migration. Earlier plans remain linked and visible. Earlier geometry and capacity show as unknown, even if the current shape is optionally displayed as a clearly labeled reference. |

### Durable model

Add one project-scoped `GrowingAreaGeometryVersion` model, with a stable version ID and the following fields. Prefer typed foreign keys and database constraints on both PostgreSQL and SQLite.

| Fields | Contract |
| --- | --- |
| `project_id`, one of `location_id`, `field_id`, `bed_id` | Exactly one owning identity. Each lookup and write scopes owner and parent to the same project. Partial unique indexes enforce one record per owning identity and `effective_from`; the same indexes support efficient latest/prior lookup. |
| `effective_from` (date), `state` (`active` or `retired`) | The next explicit entry ends the interval immediately before its effective date. Store no overlapping end date. A durable marker on the identity distinguishes `not_yet_available` before a reliably dated creation from `unknown` before the first legacy evidence, including after backfill. A retirement record keeps the immediately preceding physical facts for display and audit while making the identity unavailable. |
| Parent location or field FK on the version | Parcel versions point to a location identity and bed versions to a parcel identity. Location versions have no parent. Resolve each parent at the same date. Persist a changed parent only for a deliberate correction of the selected interval or a supported grouped transition. New identities use deliberate relationships. An inactive or unknown parent makes the child unavailable or unresolved for new assignments without deleting its own historical geometry. |
| `length_m`, `width_m`, `confirmed_area_sqm`, `measurement_basis` | Dimensions, declared area, confirmed boundary, or unknown. Positive finite recorded measurements only, using existing public units and rounding conventions. A boundary-derived area may have genuine rectangle dimensions or no dimensions. Never derive apparent measured sides for arbitrary polygons. State and provenance distinguish genuinely measured values from legacy observations. |
| Optional `boundary_wgs84`, `shape_kind`, `source`, `precision`, `anchor` | Use the validated GeoJSON Polygon and measurement rules in the [Map design](growing-area-map-design.md#geographic-and-schematic-geometry). The optional metric anchor describes the origin and bearing for parcel-relative positions. Without it, positions remain relative and are not fabricated on a geographic map. |
| `origin` (`legacy_observation`, `new_area`, `physical_change`, `retirement`), optional original season reference, revision token | Freeze the effective date when the user chooses the season. The optional reference explains the decision and is never the chronology key. Existing actor, revision, batch and project checkpoint functionality records writes. The row survives audit cleanup. |

Prefer sparse versions. A name, note, color, layout move or unchanged save writes no physical version. A correction targets one specific version ID and token and updates its selected facts atomically. Its interval is unchanged. Other versions keep their existing facts. A real change writes a new entry. An entry for the same effective date yields a conflict and offers deliberate correction of that existing entry. Inserting a new boundary before a scheduled entry affects only the intervening interval.

A minimal recorded transition has a project, effective date, existing batch reference and one or more source-to-destination edges, each with a relation such as split, merge or relocation and an evidence flag. Store only real transitions. A split or merge requires predecessor links even without geodata. A relocation to confirmed disjoint soil has no transfer of rotation history. Protect edges against foreign-project links, self references, nonchronological edges and cycles. Retain them with the geometry records.

## Resolution and API

Use one server-side resolver for a project, area identities and a business date. Bulk-select the latest version with `effective_from <= as_of` for each identity, plus its next boundary, and resolve historical ancestors at that date. Return availability separately from known measures. Include `version_id`, `effective_from`, `next_effective_from`, `status`, `parent_id`, measurements, optional geometry and a source/basis flag. A current display fallback may be requested for unknown legacy entries and is clearly labeled, excluded from calculations and never written as historical fact. Unknown geometry is neither zero area nor proof of free capacity.

Use the same view date in List, Graphic and Map. For a past or future season use its start date. For the current season use the same project business date the season selector uses, constrained to that season. This permits a legacy observation within the current season to be shown accurately. For dates in a gap, a date-based read still resolves the existing interval, but a new physical version requires choosing a real project season in the first release. Editing season labels or dates later does not silently move a committed geometry boundary. If a view's season now contains multiple physical intervals, show the view date and interval and allow an explicit date within that season when needed. Report consumers use the relevant operation dates instead of the view date.

A season beginning 2025-10-01 and ending 2026-09-30 resolves 10 m² for Bed 42. The season beginning 2026-10-01 resolves 15 m² after its physical change. A plan occupying September 25 through October 15 crosses both intervals under the same references and allocation. Allocation is checked against 10 then 15 m². A further 18 m² effective 2028-10-01 stays intact if an intermediate 16 m² version is inserted effective 2027-10-01. Lookup follows the dates even if the IDs or season names are in a different order.

Expose scoped, paginated geometry reads through a separate season/date-aware contract. Keep existing current-geometry reads compatible while consumers migrate. Use a separate write operation with a dry-run preview and explicit confirm:

1. Preview receives an area or creation parent, selected season, action, version precondition and proposed measurement/boundary. Derive the date on the server. Return old/new values, affected intervals and descendant/plan counts with paginated details, blocking conflicts, warnings and a short-lived bound proposal token. A correction explicitly identifies the target version.
2. Confirm rechecks membership and write access, validates the full proposal again under a transaction, and rejects changed version, occupancy, layout anchor or topology with a stale-preview conflict. Bind the token to actor, project, normalized inputs, involved versions and affected dependency state. Never trust affected IDs or permission results supplied by a client.
3. Serialize relevant concurrent updates with one stable lock order across the structure, plan writers and season-copy path, then update the domain record and project history in the same transaction. Use an idempotency key bound to project, actor and proposal. A failed group write leaves no partial versions, reassignments or audit events.

Anchor all identities, seasons, ancestors, plans and lineage edges to the active project. Use the existing project membership and guest/share restrictions. Reuse the project-history authority where an operation is itself an Undo or project restore. Read-only API tokens remain read-only. Bound vertices, areas, result size and timeline queries. Use revalidation tests with both SQLite and PostgreSQL instead of relying on a preview as permission to write.

## Conflict, rotation and reporting rules

- **Already used and continuing areas.** Treat an area as used if it has linked plans, recorded harvest or other agronomic history, or descendants that do. When membership or occupancy spans the boundary, check each affected date slice using the existing firm-occupancy and succession rules plus the version's capacity. Include perennials and overwintering annuals by actual/projected occupancy, including earlier actual field establishment. A smaller footprint that no longer contains a used child or required position, or cannot hold planned area, blocks commit. Unknown required capacity or child geometry prevents a positive clearance. The preview names the affected plans, versions and dates. A future edit can be selected where the conflict ends.
- **Retirement, relocation, split and merge.** Reject a retiring parent with affected continuing or future plans, active children left without an available parent, or incompatible pending target assignments. A deferred transfer needs its own explicit workflow. Do not clear the plan's references or move it implicitly. Check explicit future versions that would become unreachable and require a supported resolution. Historical plans, tasks and harvest remain connected to their original IDs.
- **Individual plants.** Keep the #1015 stable stem IDs, authoritative counts and relative metres. Project them through the selected version's agreed origin/bearing when the anchor exists. Check actual stem points against the new measured or geographic footprint including boundary changes, under the same parcel locks as stem writes. A translated/rotated GPS correction can adjust the georeferencing frame only as explicitly previewed. Physical shape edits must not rescale or move a stem automatically. Never treat an estimated canopy as exclusive occupation. Parcel-direct plans keep their original parcel and are excluded from rotation remapping.
- **Season copying and parcel rotation.** Resolve source membership/area at the original occupancy start or origin-season start for an undated draft. Resolve target availability and size at the proposed occupancy date or destination-season start for a draft. Check all target slices the plan occupies, including later explicit geometry changes. Carryovers keep references and counts. Reject an unavailable or unresolved proposed bed, and do not use the current row as a historical substitute. Store source/target version IDs alongside the existing undrifted copy basis. On a changed basis, re-preview rather than silently rescale recorded source facts.
- **Crop-family history after split or merge.** Follow lineage onto physically shared ground. If validated old and new polygons support an overlap test, treat source history as relevant only for overlapping ground. If geometry or occupancy precision is insufficient, report that the crop-family clearance is unverified and retain source histories as conservative context. Use the existing confirmation path only for known conflicts where allowed. No automatic green assessment for unresolved overlap. A whole spatial attribution engine and editing the lineage itself can remain future work.
- **Occupancy and yield.** Use effective area and availability for each date slice when presenting space used or free. Plan `area_usage_sqm`, `quantity`, recorded harvested-area allocations and actual harvest remain immutable by a geometry write. Compute existing historical yield-per-area from its recorded plan allocation or harvested-area denominator. Without a suitable denominator show unavailable. Avoid substituting historical or current whole-bed area for a missing planting fact. Use historical parent relationships for report filters and labels. Show partial results explicitly where lineage or historical geometry is unknown.

## Migration, history and import

1. Add the schema and measure a single legacy observation per available identity at a fixed project cutover date. Use current stored dimensions, consistent current derived/declared area, and existing parent IDs at that date. Do not create geographic boundaries from canvas positions or address hints. Preserve layout rows, current public IDs, every plan/harvest association, and original measurement fields during the cutover. Record an explicit unknown measurement on a version when the currently stored evidence is absent or contradictory.
2. Allow historical backfill only in a separate, reviewed data path with credible evidence of both effective date and values. Existing revision snapshots can support a targeted backfill where the interval is proven, but absence of entries is no proof. Do not infer old geometry from today's fields. Verify migration forward/back on synthetic data, including legacy areas, mixed nulls and older plan history. Once geometry versions have been written, a destructive downgrade is a restore procedure with an export/backup, not an app toggle.
3. Move List, Graphic, Map, direct-plant position checks, reports and copy/rotation to the resolver before exposing physical mutation. Route present-dimension CRUD, bulk-create, duplicate/import and restore through the same invariant. Legacy physical PATCH on a used area should require a preview/confirm rather than bypass the timeline. Protect references at the database/model deletion boundary too, including descendants and plans. Normal removal is retirement. Restricted hard removal may remain for a demonstrably unused erroneous identity with only its initial setup record, no scheduled changes, lineage, references or dependents. Treat whole-project destruction under its existing authorized explicit lifecycle and migration tests.
4. Register geometry versions and lineage with the existing history/checkpoint model in parent-first restore order. Store version IDs, dates and previous/new facts in the same batch as each operation. Undo is a checked inverse through the domain service with current dependencies and token validation. Reverting an unused accidental future insert may cancel it as an explicit audited schedule change. Once relied on by dates/plans or a later explicit version, the inverse needs a scoped correction/compensating change or must report a conflict. Whole-project restore must preview geometry impact, protect later explicit versions and retained references, and use the same conflict checks when applying a historic snapshot. Keep historical data reachable, including when generic audit cleanup removes an earlier action. Do not extend the generic audit retention period.
5. Export a selected dated snapshot with status, measurement basis, date and version provenance. Offer full version timelines only through an explicitly scoped project export. GeoJSON is a geographic exchange, not authority to rewrite identities or intervals. Import into a draft, validate geometry, source rights, parent hierarchy and permissions, and show an explicit version/season mapping and conflict preview. Replays of the same confirmed operation are idempotent. Existing versions stay intact unless an authorized correction named its target.

## UX and delivery

For a used area, List/Map opens a compact preview showing old and new measurements, selected effective season or correction interval, what continues afterwards and affected areas/plans. The available choices are **Physical change from season** and **Correct measurements or position**. Use separate labeled retirement, relocation, split and merge actions as their safely supported workflows become available. On conflicts present the affected plan and date and let the user cancel or choose a safe effective season. Same-version correction only requires confirmation when it affects used history. Names and schematic-only edits keep their ordinary workflows. Past views display modest Historical, Retired, Unknown or Current reference labels, and unavailable areas stay out of new assignment pickers.
