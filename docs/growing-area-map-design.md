# Growing Areas map and aerial imagery

Decision record for [#915](https://github.com/OpenFarmPlanner/planner/issues/915), 2026-11-25. The optional fourth view uses OpenLayers in React. List remains the primary creation workflow and Graphic arranges existing areas on the schematic canvas. Map edits a geographic footprint when one is recorded. Physical edits to existing growing areas require the [season-effective history foundation](growing-area-geometry-history.md) from [#916](https://github.com/OpenFarmPlanner/planner/issues/916).

## Editor spike

The [standalone spike](../frontend/spikes/growing-area-map/) uses the repository's React, Material UI and Vite with OpenLayers 10.11.0, which is BSD-2-Clause. Its synthetic site contains a parcel and 54 beds in a local metric coordinate plane. It has its own package lock, entry point and browser tests. The application build, router, demo, service worker and dev-server dependency scan (`optimizeDeps.entries`) do not load it. It uses no tiles, address lookups, accounts or project data. [OpenLayers license](https://github.com/openlayers/openlayers/blob/v10.11.0/LICENSE.md) · [Releases](https://github.com/openlayers/openlayers/releases).

| Operation | Result |
| --- | --- |
| Select, pan and edit | Hit testing picks the smallest visible shape. A labeled select exposes the same features without requiring a pointer. The view starts without editing interactions. |
| Draw and modify | `Draw` creates irregular polygons and rectangles. Rectangles use `createBox()` in the editing projection. `Modify` changes vertices. Adding `Snap` after the active drawing/editing interaction lets it process the event first. The browser test confirms a corner placed near a bed vertex snaps to that exact coordinate. |
| Move and transform a hierarchy | `Translate` moves a feature collection containing the selected area and its descendants. Rotation and uniform resize apply OpenLayers geometry operations to the same collection around one saved metric anchor. A test transforms the site through the parcel to both the first and last bed. Arbitrary vertex edits stay on the selected feature. The production preview checks child containment after either operation. |
| Undo and cancel | An edit session holds a working copy, a pre-gesture snapshot and a bounded undo history. Undo restores one edit and Cancel restores the entire working copy. Keeping the preview changes in-memory state. Production commits only through the validated history-aware API. |
| Touch and keyboard | Touch selects a bed and activates editing. Labeled coordinate and transform controls cover drawing, vertex changes, moving, rotation and resizing without dragging. An outline and selection text identify the target. Production needs localized number parsing, instructions and screen-reader announcements for outcomes. |

The spike uses OpenLayers primitives directly. OpenLayers documents scale/rotation built on a custom Modify interaction. The prototype validates shared-anchor transforms with numeric input, so a custom pointer rotation/resize handle can follow after the accessible controls. farmOS-map is MIT, uses OpenLayers and adds controls for tasks like layer switching, geocoding, popups and printing. Its dependency surface offers no concrete advantage for the required hierarchy editing, project-scoped validation or Undo boundary. [OpenLayers transform example](https://openlayers.org/en/latest/examples/modify-scale-and-rotate.html) · [farmOS-map package](https://www.npmjs.com/package/@farmos.org/farmos-map).

Vite 8.3.8 built a 333 kB minified OpenLayers chunk (93 kB gzip) and a 431 kB spike shell (135 kB gzip, including React and MUI). CSS totaled 2 kB gzip. Headless Chromium on the Cloud runner applied the 54-bed numeric transform and waited for two animation frames in 21–34 ms over 12 warm samples. The result indicates feasibility for this dataset on this machine. Test panning, snapping and tessellation on a lower-powered phone and at representative larger project sizes before setting a production budget. Reuse the already-loaded React/MUI shell and lazy-load OpenLayers only for Map. Browser tests covered 375, 768, 1024 and 1440 px and 800 × 375 landscape.

Run it from the repository root with the application dependencies installed.

```sh
npm ci --prefix frontend
npm ci --ignore-scripts --prefix frontend/spikes/growing-area-map
npm --prefix frontend/spikes/growing-area-map run build
npm --prefix frontend/spikes/growing-area-map run dev -- --port 14191
```

Stop the dev server before running the browser tests, which start their own preview. Install Chromium with `cd frontend && npx playwright install chromium`, or set `SPIKE_CHROMIUM` to a locally installed Chromium executable. Test screenshots show the editing controls in use.

```sh
npm --prefix frontend/spikes/growing-area-map test
```

## Imagery and fallback

A registry entry records the stable provider and layer IDs, official HTTPS service origin and request template, output format, matrix set and zoom bounds, regional coverage, data/service terms, visible attribution, review date and availability. Keep the allowlist in application configuration and ship disabled entries until verified. A provider adapter handles WMTS capabilities and matrix names or a fixed approved tile template. Registry entries have no access to private geometry or user records. Providers can be disabled or replaced without altering stored geometry. Preserve the basemap choice locally per provider and location and recalculate availability from geographic coverage on every location change. National coverage is separate from the much larger bounds advertised by a global matrix set.

| Candidate | Verification and rollout decision |
| --- | --- |
| **Austria · basemap.at orthophoto** | First candidate. The operator lists WMTS in EPSG:3857 and yearly imagery with about 29 cm nationwide pixel resolution and 15 cm in some regions. The linked live capabilities URL is `https://mapsneu.wien.gv.at/basemapneu/1.0.0/WMTSCapabilities.xml`, advertised as XML. CC BY 4.0 permits commercial and private use without a fee. Display linked “Datenquelle: basemap.at” on the map. |
| **Netherlands · PDOK RGB open aerial imagery** | Verified in a deployed government viewer. The official RGB WMTS is `https://service.pdok.nl/hwh/luchtfotorgb/wmts/v1_0?service=WMTS&request=GetCapabilities`. Rijkswaterstaat's published loaded service uses KVP, `Actueel_ortho25`, `EPSG:28992`, 256 px tiles and matrix levels 00–19. PDOK also documents a more detailed current layer, with coverage and resolution varying by acquisition. Its open imagery uses CC BY and is free for all applications. Read the live matrix names for the chosen layer, and prefer a compatible display matrix where available. Use the provider/data credit from metadata, with a link to the PDOK dataset and the applicable CC BY terms. |
| **Spain · IGN/CNIG PNOA Máxima Actualidad** | Regional candidate. The official WMTS is `https://www.ign.es/wmts/pnoa-ma?service=WMTS&request=GetCapabilities`. Its current mosaic uses countrywide acquisition coverage, with high-resolution surveys in some areas. IGN documents JPEG in EPSG:3857 through level 19 and CC BY 4.0-compatible terms for eligible products and services. Use the PNOA/IGN attribution specified for the resource. Verify island and border coverage from official metadata before enabling. |
| **Street map and geometry** | Austria's documented basemap.at street layer is a candidate under the same terms and separate matrix verification. A public community OSM tile endpoint needs independent operator-policy and capacity approval for the actual deployment. The first release can always use a clearly labeled geometry-only background. Regions with no approved service default to geometry. |

The published endpoints require no credentials for the open data layers. The sources consulted do not establish a numeric throughput commitment or an SLA for the selected imagery endpoints. Treat public access as interactive and bounded. Request only visible tiles, cap concurrent work per view, honor HTTP caching headers and provider terms, and cancel queued requests on close or on a location/layer change. No bulk download, prefetch, service-worker tile cache, offline tile package or proxy cache by default. Handle persistent failures with a circuit breaker for the session and a deliberate retry, with backoff and `Retry-After` when observable. OSM's standard tile policy has additional restrictions on offline use, attribution, referrers and caching. The street map fallback needs a separately verified deployment decision if an approved regional layer is unavailable.

Rijkswaterstaat's loaded service verifies that PDOK can back a deployed map. The Austrian product page and its linked WMTS endpoint were verified through the public catalogue and an XML content-type response. The Cloud shell and browser tunnel refused direct WMTS access. Raster decoding and live cache/CORS headers from the OpenFarmPlanner origin remain an enablement test for both services. Austria is the first pilot candidate, with PDOK as a verified regional option and geometry-only available independently. Before enablement, retrieve capabilities and one visible public sample tile from the application origin, decode the image, record the actual layer/format/matrix and HTTP cache/CORS headers, and verify attribution. Use a public point such as Vienna's city centre as test data. Exercise a second viewport outside coverage and simulate HTTP 429, offline and a failed tile using local fixtures. Keep this live check outside required regression CI so provider incidents do not block app changes.

## Location, privacy and degraded states

Reuse the shared Growing Areas location selector and view switch. An existing single location is selected automatically. For multiple locations, preserve the current selection and switch Map state with it. An empty project keeps the existing onboarding affordance to add a location. If a location has a confirmed footprint, fit it. Otherwise use a complete, valid latitude/longitude pair as a starting viewport. A location without either shows coordinate entry and manual navigation from a neutral map. Store typed pairs or an explicitly saved map location through the scoped Location API. An existing address is a display/edit field by default. Nothing submits it automatically.

Start with geometry only. Enabling a supported imagery or street layer in Map shows which service receives requests, including the visitor IP and the visible area implicit in tile grid indices. At that point send only normal HTTPS resource requests for the visible tile indices. Keep project IDs, polygons, crop/plan facts, addresses and exact stored coordinates out of provider URLs, headers and telemetry. Allowlist the relevant images/connect origins in the deployed client. Use an origin-only cross-origin referrer where allowed and required by that service. Cancel pending work on exit. List, Graphic and project/demo creation instantiate no tile or geocoder clients. No device-location permission is requested.

The initial discovery chooses manual pan and coordinates without a geocoder. A later optional search requires a permitted service, explicit submission and disclosure for the query. Do not re-use provider inputs for analytics. Public Nominatim has an application-wide maximum of 1 request/second, requires identification and attribution, forbids autocomplete, and asks that confidential material stay out of requests. It is excluded from the initial implementation. [OSMF Nominatim policy](https://operations.osmfoundation.org/policies/nominatim/).

| Condition | User-visible behavior |
| --- | --- |
| Missing coordinates | Explain that Map has no location anchor. Offer manual coordinates/navigation. List and Graphic still work. |
| No approved coverage or suitable imagery at the current zoom | Explain that imagery is unavailable here. Offer any approved overlapping layer or the geometry background. |
| Offline | Keep already loaded confirmed and draft vectors, label offline, and disable server commit while retaining the unsaved draft. Never silently write it on reconnect. |
| Tile/network error | Keep the vectors and attribution for any raster still visible. Show which layer failed and offer retry or geometry only. Avoid repeated fallback traffic. |
| Onboarding or a session without access | Use existing project permissions and demo handling. Guest/member read access never grants permission to alter geographic geometry. Synthetic examples stay geometry-only. |

## Geographic and schematic geometry

Store an optional two-dimensional RFC 7946 GeoJSON `Polygon` with finite `[longitude, latitude]` coordinate pairs in WGS84 on each durable geographic geometry version. Represent a rectangle as a polygon with rectangle intent and, only when measured in a metric plane, its orientation and sides. Persist provenance (`manual` or future import), confidence/precision at input, measurement basis and the committed metric area. Store no provider image or geocoder response. Initially support a single exterior ring and explicitly reject holes/multipolygons and antimeridian- or pole-crossing shapes until supported. Bound vertices and payload size on the server, normalize winding and ring closure, reject repeated/degenerate or self-crossing rings, and validate parent containment and project relationships. Ignoring a render warning never overrides server validation. [RFC 7946](https://www.rfc-editor.org/rfc/rfc7946).

Use display CRS only for display. For local edits, project all related shapes to one suitable metric CRS chosen for that site's extent and latitude. Calculate lengths, spacing, rotation and transforms there and reproject vertices to WGS84 before saving. For area, use an ellipsoidal/geodesic calculation, or a tested local equal-area method with a defined error tolerance. Reject unsupported extents for editing if accuracy cannot be established. Never apply degree values as metres or trust the area of raw Web Mercator coordinates. Reuse the separation between metre calculations and pixels in [Growing Areas geometry](../frontend/src/pages/graphicalFieldsGeometry.ts), including containment/short-path policy where applicable. Use Austria and Netherlands fixtures at their actual latitudes to catch Web Mercator errors.

The schema has exactly one chosen area basis per version. A confirmed boundary produces the confirmed metric area. For measuring rectangles, genuine width/length may be stored when consistent with the basis and tolerance. For irregular polygons, keep these fields absent unless they describe separately recorded measurements with clear semantics. Dimensions-only or declared-area versions continue to work when a boundary is absent. Location currently derives area from width × length. Field and Bed override area when both dimensions are set. Update those model/API projection rules and the row editors before enabling conflicting bases. Continue to expose a compatible `area_sqm` read value from the effective version and require a deliberate mode change before replacing its basis. Never write arbitrary rectangle sides into physical measurement fields just to render a polygon.

Graphic stores independent local positions. For a polygon that needs a schematic equivalent, let a user preview a local metric outline or an approximate rectangular symbol. When they choose a graphical aspect ratio `r`, derive virtual sides `sqrt(area * r)` and `sqrt(area / r)`. Confirm only schematic position/aspect/rotation in the layout and label it approximate. The displayed and reported physical area remains the confirmed geometry area. Editing or panning Graphic never georeferences or changes measurements. Distances and capacity for irregular outlines use the original metric shape once supported, with an explicit approximation indicator for incomplete geometry.

A geographic edit is a draft until permissions, current version, projected child and continuing-plant constraints, and season-effective classification have been validated by the server. The write contract binds project, area, effective season/version, existing revision token and full validated proposal. A held group transformation previews its affected descendants and commits atomically or leaves the state untouched. Import/export supports WGS84 GeoJSON as an interchange representation. Association with existing areas and commit still go through the same versioned API and authorization. The history prerequisite, migration and acceptable treatment of rotation lineage belong to [#916](https://github.com/OpenFarmPlanner/planner/issues/916).

## Implementation and acceptance plan

1. **[#1247](https://github.com/OpenFarmPlanner/planner/issues/1247) · Map shell and manual geometry.** Add the lazy optional location-scoped Map with geometry-only available by default and localized controls in all seven UI languages. Support rectangles and irregular polygons with explicit edit mode, accessible coordinates and cancellation. Wire production writes only when the #916 history foundation can represent the requested operation. Until then, keep edits to existing physical areas read-only or in unsaved preview. Prove permission, invalid topology, child outside parent, conflict/retry, non-georeferenced fields, first enablement, cross-border and zero-network List/Graphic/demo cases. Allow a regional layer only after the separate live check above. Use local fixture imagery for regression tests and protect plan data when using an external layer.
2. **[#1248](https://github.com/OpenFarmPlanner/planner/issues/1248) · Existing areas and conversion.** Preview dimension-accurate placement and the placement of descendants in a common metric plane. Keep the confirmed area across toggles, reloads and import/export round trips. Test square metres at different latitudes, area preservation for a concave outline, width/length precedence, relative tree offsets, bed utilization and pre/post effective seasons. Require the history-aware work item before any physical rewrite of an in-use area. Offer regular placement through the List's existing bulk workflow rather than duplicating it on the map.
3. **[#955](https://github.com/OpenFarmPlanner/planner/issues/955) · Import or recognition later.** Import drafts still use the same validation, authorization, consent, review and audit path. Separate imagery license and data-flow checks apply before any external recognition or processing. The Map must work without recognition or a commercial API.
