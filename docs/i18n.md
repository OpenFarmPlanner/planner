# Internationalization (i18n)

OpenFarmPlanner supports **German (`de`)** and **English (`en`)**.

Three concerns are deliberately kept apart. Confusing them is the most common
i18n bug, so each has its own storage and its own rules:

| Concern | Owner | Translated? | Where it lives |
| --- | --- | --- | --- |
| **UI language** | the *user* | yes, via locale bundles | `accounts.UserProjectSettings.ui_language` + `localStorage` |
| **Public crop-library content** | the library | yes, via translation rows | `CropSpeciesTranslation`, `PublicCropTranslation` |
| **User project content** | the user's project | **never** | the project tables, verbatim |
| **Regional crop terminology** | the *project* | regional display override, not UI translation | `Project.region` + `CropSpeciesTranslation.regional_names` |

Project crop records keep their stored `Crop.name` unchanged for editing,
history, and exports. Read-only project crop surfaces may additionally show
a localized species display name when the crop is linked to `CropSpecies`;
the project crop API exposes that as `crop_display_name` beside the
verbatim `name`, and planning APIs expose the same concept beside
`crop_name`.

`Project.region` controls region-specific German crop terminology for every
member of the project. The default is Germany, which uses the canonical German
crop-library name. Austria and Switzerland may override the display name through
`CropSpeciesTranslation.regional_names`; if no override exists, the canonical
translated name is shown. This setting is deliberately independent from the
account/UI language preference.

All project-facing crop labels use the same display contract:

- backend serializers and aggregate services resolve linked species names with
  `farm.services.crop_display.resolve_crop_display_name()`, which only trusts a
  species name once the species is `published` — a still-`proposed` or
  `rejected` species falls back to the verbatim `Crop.name`;
- APIs keep raw project identity fields (`name`, `crop_name`) unchanged and
  add `crop_display_name` / `crop_display_language_code` for display;
- frontend components format visible crop labels through
  `frontend/src/crops/cropDisplay.ts`, including selectors, tables,
  filters, charts, dialogs, and confirmation text.

Do not denormalize a translated species name into planting plans, seed demand
rows, yield summaries, or other project entities. The crop id stays the
identity; the localized label is resolved at the API/UI boundary.

## 1. UI language

### Resolution order

The effective language is the first of these that yields a supported code:

1. the signed-in user's stored preference (`ui_language`), unless it is `auto`;
2. the locally stored choice (`localStorage["ui.language"]`) — used for guests
   and to render the correct language before `/auth/me/` resolves;
3. the detected browser language (`navigator.languages`, then
   `navigator.language`);
4. English.

Browser tags are normalised to a base language:

- `de`, `de-AT`, `de-DE`, `de-CH`, `de_DE` → `de`
- `en`, `en-US`, `en-GB`, `en_GB` → `en`
- anything else → English

**The browser language is only an initial value.** Once a user picks a
language, that choice is stored and wins on every later visit; it is never
silently re-overridden by the browser language, survives reloads and new
sessions, and takes effect without signing in again.

### Stored values

The stored preference is one of `auto`, `de`, `en`. `auto` means "follow the
browser language" and is the default for accounts that never made a choice —
which is exactly the behaviour those users had before the setting existed.

- **Guests**: `localStorage["ui.language"]`.
- **Signed-in users**: `PUT /api/auth/account/language/`, exposed on
  `/api/auth/me/` as `ui_language`. The resolved value is *also* mirrored into
  `localStorage` so the next page load starts in the right language instead of
  flashing the wrong one.

Production public pages are prerendered as German HTML for SEO. Before the SPA
bundle loads, `frontend/index.html` runs a small synchronous preboot resolver
with the same local-storage/browser/fallback priority used by
`resolveInitialLanguage()`. If that resolver selects English, it updates
`<html lang>` immediately and hides the German prerendered root until React has
committed the first app render. This prevents the production-only flash where
an English visitor could briefly see the German prerendered landing page while
the hashed JavaScript assets were still loading.

### Guest chooses a language, then signs in

| Account preference | Result |
| --- | --- |
| `auto` (no explicit choice) | the local choice is **promoted** to the account |
| `de` or `en` (explicit) | the **account wins**; the local value is overwritten |

Rationale: a guest who just picked a language would be surprised to lose it on
sign-in, but an explicit per-account setting made on another device must not be
clobbered by a leftover value in a shared browser.

### Where the switcher lives

- **Public pages** — landing page header, all auth pages (via `AuthPageShell`),
  imprint / privacy / terms (via `PublicPageLanguageBar`). On the legal
  documents `LegalDocumentLayout` places the dense switcher beside the compact
  print action in the title header on wider screens; on phones the controls
  wrap below the centred document title.
- **Signed-in app** — the account menu (desktop and mobile) under a "Language"
  section, and Account settings → *Language*.

There is deliberately **no project-level UI language**: two members of the same
project must be able to use it in different languages at the same time. There
is also no project default language for exports or reports, since no concrete
use case exists yet.

### Accessibility

The switcher shows language *names* ("Deutsch", "English") — never flags,
which denote countries rather than languages. It is keyboard operable, exposes
the current value through `aria-checked` rather than colour alone, has an
accessible name that states what the control does, and uses 44px minimum touch
targets.

On phones the compact (`dense`) variant used in the public headers drops its
decorative globe and chevron icons and keeps the language name alone — never
an icon-only control — so the header rows it shares with the centred logo stay
readable on narrow screens.

## 2. Translating the UI

Translations live in `frontend/src/i18n/locales/<lang>/<namespace>.json`,
grouped by functional area (`common`, `navigation`, `crops`, `plantingPlans`,
`auth`, `account`, …). Keys are descriptive and hierarchical
(`crops:form.growthDurationDaysHelp`), never auto-numbered.

**Both bundles must define the same keys.** This is enforced by
`frontend/src/__tests__/i18nKeyParity.test.ts`, which fails on missing keys,
extra keys, blank values, and mismatched `{{interpolation}}` placeholders.

Do not hardcode visible German or English text in components, and do not use
`t('key', { defaultValue: 'German text' })` — a German default leaks into an
English UI. Add the key to both bundles instead.

### Adding a language

1. Add the code to `SUPPORTED_LANGUAGES` in `frontend/src/i18n/languages.ts`.
2. Add the code to `SUPPORTED_LANGUAGE_CODES` in `backend/config/languages.py`.
3. Copy `frontend/src/i18n/locales/en/` to the new code and translate it.
4. Register the bundles in `frontend/src/i18n/config.ts`.
5. Add an MUI DataGrid locale to `frontend/src/components/data-grid/localeText.ts`.

Nothing else is language-specific. Existing crop content simply falls back
(see below) until translations are added.

## 3. Public crop library

### Model

A crop species is **language-independent**; its names are translations of that
one record. A German and an English name are never two species.

```
CropSpecies                  language-independent, stable id
  ├─ name                    canonical reference label (not a UI label)
  └─ CropSpeciesTranslation  (species, language_code) unique
       ├─ common_name        "Tomate" / "Tomato"
       ├─ regional_names     e.g. {"austria": "Paradeiser"}
       └─ synonyms           search aliases, never direct display
                             (which of the two a regional term belongs in:
                              see crop-taxonomy-guidelines.md §4)

PublicCrop                the concrete crop/variety, language-independent
  ├─ crop_species            → CropSpecies
  ├─ variety                 proper name, never translated
  ├─ notes                   original-language description (kept in sync)
  └─ PublicCropTranslation  (public_crop, language_code) unique
       └─ description        translatable public description
```

`PublicCrop.notes` remains the original-language copy so the
import-into-a-project path and older consumers keep working; the translation
rows are the multi-language source of truth and are kept in step on publish and
on edit.

### Translatable vs. not

| Translatable | Not translatable |
| --- | --- |
| species common name | variety name (a proper name) |
| public description | supplier, article number |
| editorial library text | spacings, durations, temperatures, quantities |
| | any numeric/technical field |
| | private notes, project/location/bed names |

`Tomate – Moneymaker` and `Tomato – Moneymaker` are the same crop: the species
name changes, the variety does not.

### Fallback order

For every translatable field:

1. the requested language,
2. English,
3. any other available translation,
4. a sensible technical replacement (the canonical species name, or a
   translated "Unnamed" placeholder).

For species names, the language fallback first selects the translation row and
then applies the active project's regional override for that same language.
Regional terms never fall across languages automatically: an Austrian override
on the German row does not replace an English fallback.

The API reports the language it actually served for translated values
(`display_language_code`, `description_language_code`). For descriptions,
`description_language_code` is `null` when no description text exists in any
language, including the original `notes` copy. The UI shows the discreet
"Only available in English" chip only inside the Notes/description block, only
when real description text is rendered from a language other than the current
UI language. Empty descriptions never get a language chip. Empty names,
`undefined`, `null` and raw ids are never rendered.

### Editing

One crop, with language sections — never two crops for two languages:

- **General data** — language-independent fields.
- **Deutsch / English** — only genuinely translatable fields.

At least one language version must have a description; not every supported
language has to be filled in immediately.

The public crop-library detail view is the quick entry point for missing
description translations. When the Notes section falls back to another
language, the fallback chip sits next to an “Add translation” action. That
action opens a per-language translation dialog: the delivered original or
fallback text is shown read-only, and the editor saves only the current UI
language through `PUT /api/public-crops/<id>/translations/`.

The full public crop-library edit form keeps its field-centric multilingual
notes section for people who are already editing the complete entry. The
normal Notes field edits the original-language `PublicCrop.notes` copy, and
saving that field keeps the matching `PublicCropTranslation` record in sync.
When the current UI language is different from the original language, the
same Notes section also shows an inline translation field for the current
language. Missing translations are displayed with an explicit fallback
indicator, both in the detail view and in the editor, so original text is
never presented as if it were translated.

## 4. Search and duplicate detection

**Search** spans *all* stored translations, species synonyms, and regional
display overrides, so a query in one language or region finds entries named in
another: with a German UI, searching `Tomato` finds `Tomate / Tomato`, and
searching `Paradeiser` finds the canonical `Tomate` species. The German
alias list is seeded from `crops.seed_data.CROP_SPECIES_SYNONYM_SEED_DATA` and
maintained by moderators under `/app/public-library-moderation`; see
[crop-library-architecture.md](crop-library-architecture.md) for when a
regional name becomes an alias instead of its own species. Results are shown
in the current language and project region, with the fallback chain above.
Species translations and descriptions are prefetched, so the wider search costs
a constant number of queries regardless of result count (guarded by a test).

**Duplicate detection** is based on the language-independent species plus a
normalized variety name plus the supplier — never on a localized name plus
variety. `Tomate + Moneymaker` and `Tomato + Moneymaker` are correctly
recognised as the same crop. When no species is linked, the crop's name is
resolved against every translation first; only if that fails does it fall back
to name matching, for entries that predate species links.

Variety normalization for comparison is deliberately shallow — trim, collapse
whitespace, case-fold — and **never** modifies the stored or displayed name.

## 5. API

Requests resolve their content language in this order:

1. `?language=de|en` (unsupported values are ignored, not rejected, so a stale
   link never 400s),
2. the signed-in user's stored preference (unless `auto`),
3. the `Accept-Language` header (quality values honoured),
4. English.

`config.languages.resolve_request_language` is the single implementation of
that order. Only step 4 is per-caller: it takes a `default`, which the demo
project endpoints set to German because the demo templates are authored in
German.

The frontend sends `Accept-Language` on every request, so no call site has to
remember to pass the language.

Responses carry **both** shapes:

- resolved values for the app (`display_name`, `description`, plus the
  `*_language_code` that says which language was actually served);
- the full translation maps (`translations`, `crop_species_translations`) so
  editorial and moderation screens can edit any language.

`PUT /api/public-crops/<id>/translations/` upserts a
`{language_code: description}` map. Languages that are omitted are left
untouched — "I have not written the English version yet" must not mean "delete
the English version".

## 6. Data migration

| Migration | What it does |
| --- | --- |
| `accounts.0011` | adds `ui_language`, defaulting to `auto` |
| `crops.0004` / `farm.0082` | create the translation tables |
| `crops.0005` | backfills species translations |
| `farm.0083` | backfills public-crop descriptions |

Documented assumptions, all verified by tests in
`crops/tests/test_migrations_translations.py`:

- Existing `CropSpecies.name` values were entered through a German-only UI, so
  they become the **German** translation. `name` itself is left untouched.
- English species names are written **only** where the normalized name matches
  a hand-curated entry in `crops/seed_data.py`. Nothing is machine-translated.
- Species with no curated match get German only. In an English UI they fall
  back to German and are labelled as such.
- `PublicCrop.notes` becomes the translation for
  `original_language_code`, or German when that field is empty (everything
  published before this change went through a German UI). `notes` is **not**
  cleared.
- Empty descriptions produce no row — a blank translation carries no
  information and would make "has a translation" checks lie.

Both backfills are idempotent (keyed on `(record, language_code)`) and their
reverse operations only delete translation rows, never source data.

## 7. URLs and SEO

The signed-in app needs no language in the URL: the language is resolved
reliably from the user setting.

Public pages keep their existing stable paths (`/impressum`, `/datenschutz`,
`/nutzungsbedingungen`). No `/de/…` `/en/…` split was introduced: the public
surface is four pages, and splitting them would add routing, `hreflang`,
canonical and redirect complexity for no practical gain — see
`docs/seo-and-indexing.md`.

Build-time SEO metadata (canonical URLs, `robots`, prerendered `<title>`) stays
in the site's canonical language (`seoConfig.SITE_LANGUAGE`). At runtime,
`RouteSeo` keeps `document.title` and `<html lang>` in step with the language
the user is actually reading.
