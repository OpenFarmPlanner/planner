# Internationalization (i18n)

OpenFarmPlanner supports **German (`de`)**, **English (`en`)**, **French
(`fr`)** and **Spanish (`es`)**, all four equally: the app UI, the public
pages, emails and the crop library. German is the reference bundle and the
public-page default; English is the last-resort fallback. Terminology, forms
of address and typography for every language are binding and live in the
[translation glossary](i18n-glossary.md).

Maintained React sources are guarded by the local ESLint rule
`i18n/no-hardcoded-ui-strings`. It covers JSX text and user-facing attributes,
including labels, placeholders, helper text, titles, ARIA labels,
descriptions, value text, role descriptions, and image alternative text.
Decorative images may use an empty `alt`; tests and the
vendored Gantt package are intentionally outside this application-copy guard.

Three concerns are deliberately kept apart. Confusing them is the most common
i18n bug, so each has its own storage and its own rules:

| Concern | Owner | Translated? | Where it lives |
| --- | --- | --- | --- |
| **UI language** | the *user* | yes, via locale bundles | `accounts.UserProjectSettings.ui_language` + `localStorage` |
| **Public crop-library content** | the library | yes, via translation rows | `CropSpeciesTranslation`, `PublicCropTranslation` |
| **User project content** | the user's project | **never** | the project tables, verbatim |
| **Regional crop terminology** | the *project* | regional display override, not UI translation | `Project.region` + `CropSpeciesTranslation.regional_names` |

Project crop records keep their stored `Crop.name` unchanged for editing,
history, and exports. Read-only project crop surfaces may additionally show
a localized species display name when the crop is linked to `CropSpecies`;
the project crop API exposes that as `crop_display_name` beside the
verbatim `name`, and planning APIs expose the same concept beside
`crop_name`.

`Project.region` controls region-specific German crop terminology for every
member of the project. The default is Germany, which uses the canonical German
crop-library name. Austria and Switzerland may override the display name through
`CropSpeciesTranslation.regional_names`; if no override exists, the canonical
translated name is shown. This setting is deliberately independent from the
account/UI language preference.

All project-facing crop labels use the same display contract:

- backend serializers and aggregate services resolve linked species names with
  `farm.services.crop_display.resolve_crop_display_name()`, which only trusts a
  species name once the species is `published` — a still-`proposed` or
  `rejected` species falls back to the verbatim `Crop.name`;
- APIs keep raw project identity fields (`name`, `crop_name`) unchanged and
  add `crop_display_name` / `crop_display_language_code` for display;
- frontend components format visible crop labels through
  `frontend/src/crops/cropDisplay.ts`, including selectors, tables,
  filters, charts, dialogs, and confirmation text.

Do not denormalize a translated species name into planting plans, seed demand
rows, yield summaries, or other project entities. The crop id stays the
identity; the localized label is resolved at the API/UI boundary.

## 1. UI language

### Resolution order

The effective language is the first of these that yields a supported code:

1. the signed-in user's stored preference (`ui_language`), unless it is `auto`;
2. the locally stored choice (`localStorage["ui.language"]`) — used for guests
   and to render the correct language before `/auth/me/` resolves;
3. the detected browser language (`navigator.languages`, then
   `navigator.language`);
4. English.

Browser tags are normalised to a base language:

- `de`, `de-AT`, `de-DE`, `de-CH`, `de_DE` → `de`
- `en`, `en-US`, `en-GB`, `en_GB` → `en`
- `fr`, `fr-FR`, `fr-CA`, `fr-CH`, `fr-BE` → `fr`
- `es`, `es-ES`, `es-419`, `es-MX`, `es-AR` → `es`
- anything else → English

The same mapping is implemented three times and must stay in step:
`normalizeLanguageTag()` in `frontend/src/i18n/languages.ts`, the preboot
resolver in `frontend/index.html`, and `normalize_language_tag()` in
`backend/config/languages.py`.

**The browser language is only an initial value.** Once a user picks a
language, that choice is stored and wins on every later visit; it is never
silently re-overridden by the browser language, survives reloads and new
sessions, and takes effect without signing in again.

### Stored values

The stored preference is one of `auto`, `de`, `en`, `fr`, `es`. `auto` means "follow the
browser language" and is the default for accounts that never made a choice —
which is exactly the behaviour those users had before the setting existed.

- **Guests**: `localStorage["ui.language"]`.
- **Signed-in users**: `PUT /api/auth/account/language/`, exposed on
  `/api/auth/me/` as `ui_language`. The resolved value is *also* mirrored into
  `localStorage` so the next page load starts in the right language instead of
  flashing the wrong one.

**Public SEO pages exist once per language, and each URL renders its own
language** (`src/i18n/routeLanguage.ts`, kept in step with navigation by
`RouteLanguageSync`): `/ueber` is German, `/en/about` English. Visitors still
land in their language: on the first load of a public page, a visitor whose
stored choice — or, without one, browser language (German, French and Spanish → their own version, anything else →
English) — differs from the page's is redirected to the counterpart URL
before first paint (`src/i18n/publicPageLanguageRedirect.ts` and the
`index.html` preboot). Crawlers are never redirected, so every language
version stays indexable; see `docs/seo-and-indexing.md`. Visiting a URL never
changes the stored preference; picking a language in the switcher does.

On every other route, `frontend/index.html` runs a small synchronous preboot
resolver before the SPA bundle loads, with the same
local-storage/browser/fallback priority used by `resolveInitialLanguage()`. If
it selects English, it updates `<html lang>` immediately and hides the root
until React has committed the first app render, so an English visitor never
briefly sees German markup that a static server's SPA fallback handed out.

### A choice the account does not hold yet

Every switch is also written to `localStorage["ui.language.pendingChoice"]`
(`PENDING_LANGUAGE_CHOICE_KEY`) and stays there until the account holds that
value. While it is set it wins over the account preference, and the next
signed-in load saves it. This covers a switch made while signed out, a switch
on a public page (public pages skip the `/auth/me/` probe, so a signed-in user
looks signed out there) and a switch whose save failed: none of them falls
back to the old account value on reload or in a new tab, and there is no error
message, the language simply stays. The marker is cleared only once the save
succeeded and the reloaded user carries the value, and never by an older save
finishing after a newer switch.

Earlier builds kept this marker tab-scoped in `sessionStorage`
(`ui.language.signedOutChoice`), so a landing-page choice was lost with the
tab and the explicit account value won on the next app load. That key is still
read and migrated (deprecated; remove one release after the move).

| Situation at sign-in | Result |
| --- | --- |
| Language picked in the switcher and not yet saved to the account | that choice is **promoted** to the account, even over an explicit account preference |
| Account `auto` (no explicit choice), local value from an earlier visit | the local choice is **promoted** to the account |
| Account `de`, `en`, `fr` or `es` (explicit), local value from an earlier visit | the **account wins**; the local value is overwritten |

Rationale: someone who picked a language and then signs in (or opens the app
later) would be surprised to lose it, even when registration stored a
different language on the account. A local value without that marker is only
the cached preference of the last account, so it must not clobber an explicit
per-account setting. Trade-off: on a shared browser, a choice someone made
without signing in is saved to the next account that signs in there.

`useLanguagePreference` renders in the pending language from the first
signed-in render (no flash of the account language). Signing out re-arms the
check, so signing back in after switching again works too.

### Where the switcher lives

- **Public pages** — landing page header, all auth pages (via `AuthPageShell`),
  imprint / privacy / terms (via `PublicPageLanguageBar`). On the legal
  documents `LegalDocumentLayout` places the dense switcher beside the compact
  print action in the title header on wider screens; on phones the controls
  wrap below the centred document title.
- **Signed-in app** — Account settings → *Language*. The global (kebab) menu
  has a "Language" row with a submenu only on the local Vite dev server
  (`import.meta.env.DEV`, so production and staging builds drop it). It sets
  the preference exactly like the account settings, so the choice is saved to
  the account and survives reloads and new tabs.

  On the public SEO pages (`seoConfig.PUBLIC_PAGES`) the switcher's entries
  are real links to the counterpart URL (`/ueber` ↔ `/en/about`), kept
  mounted so crawlers can follow them without opening the menu; choosing one
  also stores the choice as the preference. On auth pages and the demo page it
  switches the language in place, as before. Internal links to public pages
  always point at the current language's URL (`usePublicPagePath`).

There is deliberately **no project-level UI language**: two members of the same
project must be able to use it in different languages at the same time. There
is also no project default language for exports or reports, since no concrete
use case exists yet.

### Accessibility

The switcher shows language *names*, each in its own language ("Deutsch",
"English", "Français", "Español") — never flags,
which denote countries rather than languages. It is keyboard operable, exposes
the current value through `aria-checked` rather than colour alone, has an
accessible name that states what the control does, and uses 44px minimum touch
targets.

On phones the compact (`dense`) variant used in the public headers drops its
decorative globe and chevron icons and keeps the language name alone — never
an icon-only control — so the header rows it shares with the centred logo stay
readable on narrow screens.

## 2. Translating the UI

Translations live in `frontend/src/i18n/locales/<lang>/<namespace>.json`,
grouped by functional area (`common`, `navigation`, `crops`, `plantingPlans`,
`auth`, `account`, …). Keys are descriptive and hierarchical
(`crops:form.growthDurationDaysHelp`), never auto-numbered.

**All four bundles must define the same keys.** This is enforced by
`frontend/src/__tests__/i18nKeyParity.test.ts`, which fails on missing keys,
extra keys, blank values, missing plural forms, and mismatched
`{{interpolation}}` placeholders. **Every new or changed string is added in
all four languages in the same change** — German first, then English, French
and Spanish, using the [glossary](i18n-glossary.md). The same applies to email
templates (see "E-Mails").

Do not hardcode visible text in components, and do not use
`t('key', { defaultValue: 'German text' })` — a German default leaks into
every other UI language. Add the key to all bundles instead.

### Plurals

i18next picks `<key>_<category>` through `Intl.PluralRules`; never write
`count === 1 ? … : …` by hand. The categories differ per language:

| Language | Categories | Notes |
| --- | --- | --- |
| de, en | `_one`, `_other` | 0 is plural |
| fr | `_one`, `_many`, `_other` | **0 is singular** (`_one`); `_many` for large round numbers (1 000 000) |
| es | `_one`, `_many`, `_other` | 0 is plural; `_many` for large round numbers |

Every pluralized key needs every category of its language — a missing
`_many` silently falls back to English for a million. Because French `_one`
also covers 0, French singular forms interpolate `{{count}}` rather than
spelling out "1". `i18nKeyParity.test.ts` compares plural keys by their base
name and checks each language's categories; `i18nPlurals.test.ts` pins the
rendered text for 0, 1, 2 and 1 000 000.

### Composed strings and typography

A sentence is one key with interpolation, never several keys glued together
in code: word order differs between languages. When a label is composed
from parts that carry grammatical gender in French and Spanish (e.g. the
version-history title "{{objectType}} … {{action}}"), the French and Spanish
strings use a neutral form (an action noun: "Création : Culture « … »").

French typography: a narrow no-break space (U+202F) before `:` `?` `!` `;`
and inside `« … »`. Spanish uses `¿ … ?`, `¡ … !` and `«…»`.

### Forms of address

The app UI and emails address the user informally where the language allows
it, legal texts formally, and the provider always speaks as "we":

| Language | App UI, emails | Imprint, privacy policy, terms |
| --- | --- | --- |
| de | du | Sie |
| en | you | you |
| fr | vous | vous |
| es | tú | usted |

### Formatting

Dates, numbers and month names are formatted with `Intl` in the active UI
language — never with a hardcoded locale. `resolveLocaleFromLanguage()`
(`src/utils/numberLocalization.ts`) maps a UI language to its formatting
locale (`de-DE`, `en-US`, `fr-FR`, `es-ES`); helpers outside a component use
`getActiveFormattingLocale()`. The MUI DataGrid chrome comes from the
matching MUI locale (`src/components/data-grid/localeText.ts`). The date
input fields keep accepting `DD.MM.YYYY` in every language.

### Adding a language

1. Add the terms to the [glossary](i18n-glossary.md) first.
2. Add the code to `SUPPORTED_LANGUAGES` in `frontend/src/i18n/languages.ts`
   and to the preboot resolver in `frontend/index.html`.
3. Add the code to `SUPPORTED_LANGUAGE_CODES` and `UI_LANGUAGE_CHOICES` in
   `backend/config/languages.py` and generate the `accounts` migration for
   the `ui_language` choices.
4. Translate every namespace from `frontend/src/i18n/locales/en/` into
   `locales/<code>/` (English is the source, German the reference for
   meaning), including every plural category, and register the bundles in
   `frontend/src/i18n/config.ts`.
5. Add the formatting locale to `resolveLocaleFromLanguage()` and the MUI
   DataGrid locale to `frontend/src/components/data-grid/localeText.ts`.
6. Add the language to `SEO_LANGUAGES`, `OG_LOCALES` and every
   `PUBLIC_PAGES` entry in `frontend/src/seo/seoConfig.ts`, and its `home`
   bundle to `frontend/src/seo/publicPageMeta.ts`.
7. Add the email templates under
   `backend/accounts/templates/accounts/emails/<code>/` (see "E-Mails").
8. Update the language-version clause of the terms and the privacy policy
   in every language.
9. Check content that only exists in some languages and falls back
   explicitly — today the demo project templates (German, English; every
   other language gets the English demo).

Existing crop content simply falls back (see below) until translations are
added.

## 3. Public crop library

### Model

A crop species is **language-independent**; its names are translations of that
one record. A German and an English name are never two species.

```
CropSpecies                  language-independent, stable id
  ├─ name                    canonical reference label (not a UI label)
  └─ CropSpeciesTranslation  (species, language_code) unique
       ├─ common_name        "Tomate" / "Tomato"
       ├─ regional_names     e.g. {"austria": "Paradeiser"}
       └─ synonyms           search aliases, never direct display
                             (which of the two a regional term belongs in:
                              see crop-taxonomy-guidelines.md §4)

PublicCrop                the concrete crop/variety, language-independent
  ├─ crop_species            → CropSpecies
  ├─ variety                 original name, never translated
  ├─ notes                   original-language description (kept in sync)
  ├─ PublicCropTranslation  (public_crop, language_code) unique
  │    └─ description        translatable public description
  └─ PublicCropTradeName    (public_crop, language_code) unique
       ├─ name               optional trade name in that language area,
       │                     never a translation ("Poire jaune")
       └─ source_url         optional catalogue/retailer link
```

`PublicCrop.notes` remains the original-language copy so the
import-into-a-project path and older consumers keep working; the translation
rows are the multi-language source of truth and are kept in step on publish and
on edit.

### Translatable vs. not

| Translatable | Not translatable |
| --- | --- |
| species common name | variety name (a proper name) |
| public description | supplier, article number |
| editorial library text | spacings, durations, temperatures, quantities |
| | any numeric/technical field |
| | private notes, project/location/bed names |

`Tomate – Moneymaker` and `Tomato – Moneymaker` are the same crop: the species
name changes, the variety does not.

A variety may additionally carry one **trade name** per language, but only
where it is actually sold under that name in that language area: `Gelbe Birne`
is sold in France as `Poire jaune`. A trade name is a market fact, not a
translation, and is never machine-generated. The original name stays the
entry's identity. Design and rules:
[rfc-variety-trade-names.md](rfc-variety-trade-names.md); which names denote
the same variety: [crop-taxonomy-guidelines.md](crop-taxonomy-guidelines.md) §5.

### Fallback order

For every translatable field:

1. the requested language,
2. English,
3. any other available translation,
4. a sensible technical replacement (the canonical species name, or a
   translated "Unnamed" placeholder).

Trade names have **no** fallback. With a trade name in the requested language
the variety reads `Poire jaune (Gelbe Birne)`; without one the original name is
shown on its own, with no fallback indicator, and never another language's
trade name.

For species names, the language fallback first selects the translation row and
then applies the active project's regional override for that same language.
Regional terms never fall across languages automatically: an Austrian override
on the German row does not replace an English fallback.

The API reports the language it actually served for translated values
(`display_language_code`, `description_language_code`). For descriptions,
`description_language_code` is `null` when no description text exists in any
language, including the original `notes` copy. The UI shows the discreet
"Only available in English" chip only inside the Notes/description block, only
when real description text is rendered from a language other than the current
UI language. Empty descriptions never get a language chip. Empty names,
`undefined`, `null` and raw ids are never rendered.

### Editing

One crop, with language sections — never two crops for two languages:

- **General data** — language-independent fields.
- **one section per language** — only genuinely translatable fields.

At least one language version must have a description; not every supported
language has to be filled in immediately.

The public crop-library detail view is the quick entry point for missing
description translations. When the Notes section falls back to another
language, the fallback chip sits next to an “Add translation” action. That
action opens a per-language translation dialog: the delivered original or
fallback text is shown read-only, and the editor saves only the current UI
language through `PUT /api/public-crops/<id>/translations/`.

The full public crop-library edit form keeps its field-centric multilingual
notes section for people who are already editing the complete entry. The
normal Notes field edits the original-language `PublicCrop.notes` copy, and
saving that field keeps the matching `PublicCropTranslation` record in sync.
When the current UI language is different from the original language, the
same Notes section also shows an inline translation field for the current
language. Missing translations are displayed with an explicit fallback
indicator, both in the detail view and in the editor, so original text is
never presented as if it were translated.

## 4. Search and duplicate detection

**Search** spans *all* stored translations, species synonyms, and regional
display overrides, so a query in one language or region finds entries named in
another: with a German UI, searching `Tomato` finds `Tomate / Tomato`, and
searching `Paradeiser` finds the canonical `Tomate` species. Species names,
synonyms, regional names and additional languages live only in the database
and are maintained through the crop-species API — by moderators under
`/app/public-library-moderation` or with a crop-library API token. A fresh
database starts from the frozen bootstrap snapshot in
`backend/crops/migrations/data/`, which is never edited; see
[crop-library-architecture.md](crop-library-architecture.md) for when a
regional name becomes an alias instead of its own species. Results are shown
in the current language and project region, with the fallback chain above.
Species translations and descriptions are prefetched, so the wider search costs
a constant number of queries regardless of result count (guarded by a test).
The species search additionally reports per result whether the query matched
the official name *in the request language* or another name — another
language's common name counts as a synonym there; see the "Why a species search
result matched" paragraph in [crop-library-architecture.md](crop-library-architecture.md).

Variety search covers the original name and every trade name in every
language, so `Poire jaune` finds `Gelbe Birne` from any UI language. Trade
names are matched in the folded form of [search.md](search.md)
(`coeur de boeuf` finds `Cœur de bœuf`).

Project crops carry the same alias list as `crop_species_search_names` on
`GET /api/crops/`, so page search (Anbaupläne) finds a plan under any
species name without a request per row — see [search.md](search.md).

**Duplicate detection** is based on the language-independent species plus a
normalized variety name — never on a localized name plus variety. The variety
matches an entry's original name **or any of its trade names**.
`Tomate + Moneymaker` and `Tomato + Moneymaker` are correctly recognised as
the same crop, and so is `Tomate + Poire jaune` once `Gelbe Birne` carries
that French trade name; the duplicate candidate then reports the trade name it
matched through (`matched_trade_name`). When no species is linked, the crop's name is
resolved against every translation first; only if that fails does it fall back
to name matching, for entries that predate species links.

Variety normalization for comparison is deliberately shallow — trim, collapse
whitespace, case-fold — and **never** modifies the stored or displayed name.

## 5. API

Requests resolve their content language in this order:

1. `?language=de|en|fr|es` (unsupported values are ignored, not rejected, so a
   stale link never 400s),
2. the signed-in user's stored preference (unless `auto`),
3. the `Accept-Language` header (quality values honoured),
4. English.

`config.languages.resolve_request_language` is the single implementation of
that order. Only step 4 is per-caller: it takes a `default`, which the demo
project endpoints set to German because the demo templates are authored in
German. The demo templates exist in German and English only:
`resolve_demo_language()` maps every other supported language (French,
Spanish) explicitly to the English demo, never to a `KeyError`.

French and Spanish crop-library content is accepted by the API like German
and English (`CropSpeciesTranslation`, `PublicCropTranslation`). Until a
French or Spanish name or description exists, the fallback chain serves the
English one and reports it (`display_language_code: "en"`), so the UI shows
the "Only available in English" hint. Approving a crop species still
requires German and English names only
(`REQUIRED_PUBLIC_CROP_SPECIES_LANGUAGE_CODES`).

The frontend sends `Accept-Language` on every request, so no call site has to
remember to pass the language.

Responses carry **both** shapes:

- resolved values for the app (`display_name`, `description`, plus the
  `*_language_code` that says which language was actually served);
- the full translation maps (`translations`, `crop_species_translations`) so
  editorial and moderation screens can edit any language.

Variety trade names follow the same two shapes without a language code, since
they have no fallback: `variety_trade_name` (request language only, or
`null`) and `variety_display` (`"Poire jaune (Gelbe Birne)"` or the original
name) as resolved values, `trade_names` (`{language_code: {name, source_url}}`)
as the full map. `variety` itself always stays the original name.

`PUT /api/public-crops/<id>/translations/` upserts a
`{language_code: description}` map. Languages that are omitted are left
untouched — "I have not written the English version yet" must not mean "delete
the English version".

## 6. Data migration

| Migration | What it does |
| --- | --- |
| `accounts.0011` | adds `ui_language`, defaulting to `auto` |
| `crops.0004` / `farm.0082` | create the translation tables |
| `crops.0005` | backfills species translations |
| `farm.0083` | backfills public-crop descriptions |

Documented assumptions, all verified by tests in
`crops/tests/test_migrations_translations.py`:

- Existing `CropSpecies.name` values were entered through a German-only UI, so
  they become the **German** translation. `name` itself is left untouched.
- English species names are written **only** where the normalized name matches
  a hand-curated entry of the starter catalogue (today the frozen snapshot
  `crops/migrations/data/species_bootstrap_v1.json`). Nothing is
  machine-translated.
- Species with no curated match get German only. In an English UI they fall
  back to German and are labelled as such.
- `PublicCrop.notes` becomes the translation for
  `original_language_code`, or German when that field is empty (everything
  published before this change went through a German UI). `notes` is **not**
  cleared.
- Empty descriptions produce no row — a blank translation carries no
  information and would make "has a translation" checks lie.

Both backfills are idempotent (keyed on `(record, language_code)`) and their
reverse operations only delete translation rows, never source data.

## 7. URLs and SEO

The signed-in app needs no language in the URL: the language is resolved
reliably from the user setting.

Public pages are the exception: they exist once per language, German at the
root (`/ueber`, `/impressum`, …) and English, French and Spanish under `/en`,
`/fr` and `/es` with slugs in that language (`/en/about`, `/fr/a-propos`,
`/es/acerca-de`, …), so search engines can index all of them. The
`PUBLIC_PAGES` registry in `seoConfig.ts` is the single list of these paths;
titles and meta descriptions come from the `home` namespace (`seo.titles.*`,
`seo.descriptions.*`), German first like every other string. Which
language version of the legal texts prevails is stated in the terms and in
the privacy policy themselves ("Language versions": provided in German,
English, French and Spanish; the English version prevails). All four
versions of the imprint, privacy policy and terms say the same and cite
articles in one uniform notation (`Art. 6(1)(f)`, `§ 165(3)`); a change is
made in all four languages at once. `legalTextConsistency.test.ts` checks
that every paragraph cites the same articles and names the same numbers and
links; see the [glossary](i18n-glossary.md) for the wording rules. See `docs/seo-and-indexing.md` for canonical, hreflang and sitemap
rules.

## 8. E-Mails

Every email to a user (activation, password reset, email change, project
invitation) is written in the **recipient's** language. Internal operator
mails (registration alerts, "New user registered", `test_email`) stay
English.

### Resolution order

`config.languages.resolve_email_language` is the single implementation:

1. the recipient account's explicit `ui_language` (never `auto`);
2. the language of the triggering request, via `resolve_request_language`:
   `?language=`, then the signed-in requester's preference, then
   `Accept-Language`;
3. English.

Per email type:

| Email | Recipient (step 1) | Request (step 2) |
| --- | --- | --- |
| Activation (registration, resend) | the account | the guest's UI language |
| Password reset | the account | the guest's UI language |
| Email change | the signed-in user | the signed-in user |
| Project invitation | an existing account with the invited address | the **inviter's** UI language |

The frontend sends its resolved UI language as `?language=` on register,
resend activation, password reset and project invitation
(`getCurrentUiLanguage()` in `frontend/src/i18n/config.ts`). It is explicit
because a guest's local choice can differ from the browser's
`Accept-Language`.

Registration stores a sent `?language=` as the new account's `ui_language`,
the same way a guest's choice is promoted on sign-in (see "Guest chooses a
language, then signs in"). Without it the account stays `auto`.

### Templates

Subject and body of each email live as complete per-language files, not
gettext fragments, so a whole email can be read, translated and reviewed in
one place:

```
backend/accounts/templates/accounts/emails/<code>/
  <kind>_subject.txt      single line, no dashes
  <kind>.txt              plain-text body
  <kind>.html             HTML body (activation only)
  project_role_<role>.txt readable role label for the invitation
```

`accounts/email_templates.py` lists the email kinds (`EMAIL_KINDS`) with the
context each one needs and renders them with a fallback to English when a
language lacks a file. Links into the public website use the language's URL
(root for German, `/en`, `/fr`, `/es` otherwise); token links (activation,
reset, invitation) are language-neutral.

**A new language must ship all its email templates.** The parity test in
`backend/accounts/tests/test_localized_emails.py` fails for every language
in `SUPPORTED_LANGUAGE_CODES` that lacks one, and checks that every
placeholder is used in every language.
