## Reproduction matrix

All records below are disposable synthetic data in one authenticated project.
Supplier S denotes the existing supported `supplier_id` relation on Crop;
its non-null value is important for the database constraint reproductions.
Ordinary crop creation and replacements use the public project API.

| Case | Steps | Observed outcome |
| --- | --- | --- |
| Undelete | Create Carrot/Nantes with S; DELETE it; POST a replacement Carrot/Nantes with S; POST the old row's `undelete/` | 500; `unique_crop_normalized`; old row stays deleted |
| Revision restore | Create Beet/Boro with S and retain creation history ID; PATCH variety to Boltardy; create Beet/Boro with S; POST `restore/` using the creation history ID | 500; `unique_crop_normalized`; row stays Boltardy |
| Sibling rename | Create general Source and Source/V with S; create Target/V with S without a general Target; PATCH the general Source's name to Target | 500 while saving the sibling; original Source names remain |
| Library sync | A published Spinach/New entry is linked to project Spinach/Old with S; project also holds Spinach/New with S; POST `public-sync/` with `pull_fields=["variety"]`, no pushes and the current version | 500; original Old variety remains |
| Null supplier | Repeat the undelete case without suppliers | 200; two active rows now have identical normalized name/variety |

Expected: a structured conflict, with no partial changes and no duplicate
identity. Existing CRUD rejects a duplicate name/variety before saving.
Four supplier-backed probes reproduced twice; the null-supplier case also
reproduced twice. Each expected-409 assertion failed with the observed status.
No exception was injected to produce these failures.

## Browser observation

A throwaway Playwright script used E2E fixture setup to create an authenticated
administrator/project, then created Source, Source/V and Target/V through
normal API calls. In the real German edit dialog, it entered Target for the
general Source and pressed Speichern. At 1440x900, 375x800 and 800x375:

All three screenshots were inspected. The desktop dialog and phone fullscreen
variant show the error, but neither explains the duplicate variety. This pass
makes no broad responsive-layout claim and does not change UI code.

## Source trace

- `farm/services/crop_inheritance.py:251`: the prospective identity validator
  skips every nonempty variety. Its conflict translator recognizes only the
  general-name constraint, not `unique_crop_normalized`.
- `farm/crops/views/crops.py:499`: undelete locks the project and calls that
  general-only validator before each direct save.
- `farm/history/restore.py:322`: revision restore similarly calls the
  general-only validator and directly saves the historical row.
- Sibling renaming and library sync perform direct saves after general-name
  checks, so their variety conflicts also reach the unhandled constraint.
- With a null supplier, the database uniqueness constraint permits the
  duplicate. Prospective application validation is needed as well as precise
  constraint-to-conflict translation after rollback.

This differs from the already-fixed general-name failures in #1037 / #1040
and #1145 / #1150. Concurrent stale-group identity (#1089) and snapshot
normalization (#1085) remain separately tracked.
